# Background result delivery decisions

## Current

- Delivery policy is separate from result persistence and parent wake mechanics.
- Every terminal background completion, including `error`, is persisted to the parent Pi session before any wake is requested. A wake call is fire-and-forget and cannot confirm that the parent provider accepted the content, so marking a record consumed at call time could evict the only copy of a result after an auth, quota, or provider failure. Persisting first prevents that loss without another database or a restored child session.
- Concurrent wake requests are coalesced. One parent message per completion would enqueue multiple follow-ups, and an unavailable parent provider would turn them into repeated failed turns; coalescing removes that self-inflicted retry storm while a later completion may still request a new wake after a failed parent run.
- A failed automatic wake does not retry itself; a later eligible event — another completion, a natural parent prompt, an explicit exact read — provides the next opportunity. A result is acknowledged only after the parent turn carrying it settles successfully; an exact `AgentStatus({ agent_id })` read is session-wide and follows the same settlement rule.
- Explicit status lookup rereads current durable entries on every call, even when an in-memory completion already exists. A construction snapshot can outlive volatile retention or another extension runtime's later write; reading only on a miss would let the old continuation conceal the new one. Delivery ID selects one completion, omission selects the newest, and a durable record wins an equal timestamp.
- Persisted entries carry final result text and metadata only — no prompts, transcripts, or child-session state — and forked or new sessions ignore copied entries with a different parent session ID. Each parent-wake injection clips that body to 4000 characters and points at `AgentStatus({ agent_id })` for the remainder; persist and exact lookup are not shortened.
- There is no scheduler, join mode, unbounded retry, provider fallback, or external notification transport. Child provider, quota, authentication, content-filter, and exhausted transport-retry failures are ordinary one-shot `error` results. The session driver ORs bare `upstream_error` / `Upstream request failed` onto Pi's existing transport retry classifier; the loop itself stays Pi's.
- A result is eligible only while its origin entry is on the active branch. The branch set is read from the host at construct and `session-tree` navigation. A background spawn registers its own origin through `track-origin` at call time: the entry carrying the Agent call is born inside the turn, so a purely host-driven set would classify the run's own origin as off-branch and hide the result the caller is waiting for. `parent-preflight` and `restore` do not replace that set — the host often still omits the in-turn leaf. `session-tree` may drop the seed: by then the host reports the entry itself, or the user navigated to another branch where hiding is correct.
- An append failure is staged in the process-local fallback inbox keyed by parent session ID (`platform/process/process-state.ts`); one session's bucket never exposes or overwrites another's. The handoff survives Pi's Jiti reload; process exit drops all buckets.
- Pi exposes no ordering barrier before cross-extension `before_agent_start` or after all `session_start` handlers. The residual ordering windows are an accepted upstream limitation; revisit if Pi adds a barrier or an incident demonstrates material impact.
- Bootstrap assembles fallible Agent guidance before issuing `parent-preflight`. Pi catches each `before_agent_start` handler independently and discards that handler's complete return value on failure; committing delivery first would acknowledge a result whose message was discarded with the guidance. Non-Agent runs skip guidance and retain natural preflight injection.
- Parent `agent_end` and `agent_settled` are different delivery phases, not two names for the same hook. `agent_end` means the Working row is gone and the run's success bit is known: delivery records `parent-end`, enters `settling`, and the navigator can reflow without waiting for acknowledgement. `agent_settled` is the later moment the parent turn is actually finished: delivery runs `parent-settled`, which is the only place a presented result may be acknowledged after a successful wake, a failed wake is remembered, and a later completion may request another wake. Collapsing the two would acknowledge on a turn that has not settled, or reflow after settlement had already moved on. Bootstrap maps the Pi events onto those commands; the module never listens to Pi itself.
- Empty child text is stored as `(no output)` when the composition seam builds the delivery record. That fill is only the persisted payload the parent will see. It does not change the runner's no-output classification: a finished run with no assistant text still fails in the session runner unless the run was aborted or turn-limited.
- Explicit Clear and runtime teardown do not mint a new result. Clear closes without a completion callback, so `record-terminal` is never issued; a missing snapshot is `stillPresent: false` anyway. Delivery `dispose` saves whatever fallback is already staged and ignores later records. Results that were already persisted or staged stay.
- After `parent-preflight`, a turn that injected nothing still has a path: `parent-start` (`agent_start`) may request a follow-up wake for results that landed in that window. A turn that already injected delivery keeps `parentWakeActive`, so `parent-start` will not open another wake; the next presentation waits for settlement.

## Superseded

- Configurable next-turn delivery and session-global injection are retired. Durable origin-branch eligibility and the state-machine examples are the current authority.
- The fixed 200ms wake debounce is retired; result aggregation happens when the parent turn is prepared.

## Implementation-only

- Result-inbox helper names, debounce constants, and manager refresh calls are not delivery concepts. Bootstrap translates Pi lifecycle into delivery commands; spawn and delivery stay separate functions.
